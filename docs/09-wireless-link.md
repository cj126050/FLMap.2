# 09 · 无线链路：硬件前提与四条通路

> [02-network-and-dds.md](02-network-and-dds.md) 讲的是「有了无线之后怎么配」。这一篇讲
> **「无线从哪来」**——因为拓展坞出厂配置里根本没有无线射频，这一步绕不过去。

---

## 0. 一个必须先纠正的前提

**拓展坞（Orin Nano 载板）没有无线射频。** 实测证据（`unitree@192.168.123.18`）：

```bash
$ lspci | grep -i network
0008:01:00.0 Ethernet controller: Realtek RTL8111/8168/8411 Gigabit Ethernet   # 只有有线
$ lsusb
Bus 002 Device 001: ID 1d6b:0003 Linux Foundation 3.0 root hub                 # 没有设备
Bus 001 Device 001: ID 1d6b:0002 Linux Foundation 2.0 root hub
$ ls /sys/class/net/
docker0  dummy0  eth0  lo                                                       # 没有 wlan0
$ rfkill list                                                                   # 空
```

两个连带结论：

1. **[02](02-network-and-dds.md) 里的三种拓扑（同一路由器 / PC 开热点 / 狗做 AP）都隐含
   「狗端有 Wi-Fi」。** 在只有载板出厂配置的机器上这个前提不成立，必须先加射频。
2. **「两个 RJ45」是同一颗网卡下的两个交换口**，不是两张网卡——`ip link` 只有 `eth0`。
   所以「空闲网口接一个路由器」这条路，接上去和 `eth0` 在同一个二层里。

另外，拓展坞**没有任何外网出口**：默认路由指向 `192.168.123.1`，但该地址 ARP 是
`INCOMPLETE`、ping 不通。这解释了为什么校时必须靠 PC 的 HTTP 服务（见 [03](03-edge-deployment.md)）。

## 1. 四条通路

| | 方案 | 硬件 | 成本 | 狗端看到的网段 | 需要 root 改动 | 主要风险 |
|---|---|---|---|---|---|---|
| **A** | USB 无线网卡插拓展坞 | MT7612U 芯片网卡 | ¥50–120 | 与 PC **同网段** | 狗端 | USB 供电、天线遮挡 |
| **B** | 便携路由器插空闲 RJ45 | GL.iNet 类 | ¥150–350 | 与 PC **同网段** | 无（在路由器里配） | 多一个盒子要固定 |
| **C** | 借 Go2 自带 Wi-Fi | 无 | ¥0 | **跨网段**（12.x ↔ 123.x） | **狗端 + 运控** | 抢遥控带宽、可能影响 App |
| **D** | 5 GHz 点对点网桥 | UBNT / TP-Link CPE 一对 | ¥300–800 | 与 PC **同网段** | 无 | 体积重量，室内过重 |

**优先选同网段的方案。** ROS 2 的 DDS 发现对跨网段、跨 NAT 非常不友好，
同网段只需要处理「Wi-Fi 上多播常被丢」一个问题；跨网段要同时处理路由、NAT、
单播 Peer 三件事，而且出错时大多是**静默失败**。

## 2. 方案 A：USB 无线网卡（推荐）

### 选芯片，不是选品牌

狗端内核 `5.10.104-tegra` 自带的 USB 无线驱动（实测 `modinfo` 确认存在）：

| 驱动模块 | 覆盖芯片 | 频段 | 建议 |
|---|---|---|---|
| **`mt76x2u`** | **MT7612U** | **2.4 + 5 GHz** | **首选**，唯一自带驱动的 5 GHz 方案 |
| `rtl8xxxu` | RTL8188CU/EU、RTL8192CU/EU、RTL8723AU/BU | 2.4 GHz | 2.4 GHz 备选 |
| `mt7601u` | MT7601U | 2.4 GHz | 2.4 GHz 备选 |
| `r8188eu` | RTL8188EU | 2.4 GHz | 能用但不推荐 |

**要避开**：RTL8812AU、RTL8821CU、RTL88x2BU。这三个是市面上最常见的「双频高增益」
U 盘网卡，但内核里**没有**驱动，得 DKMS 编译。狗端虽然有 `dkms` 和
`linux-headers-5.10.104-tegra`，但 Jetson 上编外挂驱动很容易踩编译选项和符号版本
的坑——为了 1.3 Mbit/s 的负载去折腾驱动不值。

对应型号举例（认芯片不认牌子）：COMFAST CF-926AC v2、EDUP EP-AC1605。
下单前让商家确认是 **MT7612U**，不是 8812AU。

### 插上之后

```bash
# 狗端
ip link | grep wlan                     # 应该出现 wlan0
nmcli device wifi list                  # 能看到周边 AP
```

### ⚠️ 两块网卡的坑

插上网卡后，狗端会有 **两块网卡**：

```
eth0   192.168.123.18   ← 雷达(192.168.123.20) + 运控(192.168.123.161)
wlan0  192.168.50.x     ← PC
```

CycloneDDS 默认会在**所有**网卡上做发现。PC 只在 `wlan0` 那头，如果发现包从
`eth0` 出去，PC 就永远看不到话题——而 `ros2 topic list` 只是空的，不报错。

必须显式绑定：

```bash
# 狗端：只认 wlan0，Peer 指 PC
export CYCLONEDDS_URI=file://$HOME/dds_edge.xml
```

用 [config/cyclonedds_unicast.xml.example](../config/cyclonedds_unicast.xml.example) 做模板，
把 `NetworkInterface name` 改成 `wlan0`，`Peer address` 填 PC 的地址。

## 3. 方案 B：便携路由器

把 GL.iNet 之类的小路由器 LAN 口接到拓展坞空闲 RJ45，5 V 从拓展坞 USB 口取电。

**关键：必须用中继/Extender 模式（relayd 桥接），不能用路由模式。**
路由模式会让狗端落在路由器的 LAN 私网里，PC 要穿 NAT 才能到——DDS 会挂。

Bridge/Extender 模式下，路由器把下面的设备透传到上游 Wi-Fi，狗端拿到和 PC
同网段的地址，问题消失。

优点：不占 USB、不用驱动、可选 5 GHz、有网管界面、能长期固定。
缺点：多一个盒子和一根线，要绑在狗背上。

---

## 4. 方案 C：借 Go2 自带 Wi-Fi（零成本，但有硬前提）

Go2 机身自带 Wi-Fi 模块，服务手机 App 遥控，网段 `192.168.12.x`，运控在
`192.168.12.1`。运控同时有 `eth0 = 192.168.123.161`，和拓展坞在同一个二层。

意图是把运控当成一台路由器：

```
PC ──Wi-Fi──> 运控(12.1 / 123.161) ──eth0──> 拓展坞(123.18)
```

### 三个决定性前提

1. **Go2 的 Wi-Fi AP 要开着**——App 能连上就说明开着。
2. **运控要能把 12.x 和 123.x 打通**，这里分两种情况，结果完全不同：

   | 运控行为 | 狗端要不要改 | 结果 |
   |---|---|---|
   | **NAT（MASQUERADE）** | 不用 | 狗看到的源地址是 `192.168.123.161`，回复走本地二层，天然通 |
   | **纯转发（ip_forward=1 无 NAT）** | **必须加回程路由** | 否则「去程通、回程不通」，ping 有回应但回复包掉进 `123.1` 这个黑洞 |

3. **需要运控的 SSH 凭据**。`192.168.123.161:22` 是开放的，但需要密码；
   Unitree 文档里常见的默认口令 `123` 在部分批次上已不适用。

查一件事就能判定：登进运控执行

```bash
sysctl net.ipv4.ip_forward
iptables -t nat -S | grep -i masq
```

### 实测（2026-10-18，PC 直连成功）

| 项 | 实测值 |
|---|---|
| SSID | `13829973977`（App 里自设的热点名，**不是手机热点**） |
| BSSID | `7a:22:88:af:9d:29` ← **本地管理地址**，OUI 查不到厂商，属正常 |
| 频段/带宽 | **5 GHz ch149 / 5745 MHz / 40 MHz VHT**（不是 2.4 G，比预期好） |
| 信号 / 速率 | −44 dBm 起，tx 400 Mbit/s（VHT-MCS9 40MHz NSS2） |
| PC 地址 | `192.168.12.122/24`，DHCP 由狗分配 |
| 热点网关 | `192.168.12.1`，MAC 与 BSSID **完全相同** → 就是运控的无线接口 |
| 网关端口 | 22 / 80 都开，和 `192.168.123.161` 一致 → 确认是同一台运控 |

两个关键修正：

1. **别再写"Go2 AP 多为 2.4 GHz"。** 实测是 5 GHz 40 MHz，物理速率 400 Mbit/s，
   传点云绰绰有余（链路预算见 §6）。
2. **PC 默认拿不到 `192.168.123.0/24` 的路由。** 狗的 DHCP 只给 `12.x` 网段和一条
   `192.168.12.0/24` 直连路由，没有默认网关。此时 `ip route get 192.168.123.18`
   会把包丢给 PC 的**另一条默认路由**（家里路由或手机共享），表现为"ping 不通"，
   但跟狗一点关系都没有。必须先补一条：

```bash
sudo ip route add 192.168.123.0/24 via 192.168.12.1 dev wlp132s0
```

一条命令跑完全部判定（会自动补这条临时路由，`--clean` 可撤销）：

```bash
sudo ./scripts/wifi_route_probe.sh
```

延迟实测：到网关 `192.168.12.1` 20 包 0 丢包，min 1.756 / avg 2.854 / max 9.625 /
mdev 2.042 ms。但 `power_save=on` 时会飙到 avg 27.7 ms、抖动 35.9 ms ——
**做实时点云前一定关掉省电**（`sudo iw dev wlp132s0 set power_save off`，
脚本会自动做，重连后恢复 on，不写配置）。

### 实测：拓展坞不通，但「为什么不通」还差一步

补上路由后四条 ping：

| 目标 | 2026-10-18 22:43 | 22:49 重测 | 说明 |
|---|---|---|---|
| `192.168.12.1`（运控无线口） | 通 1.851 ms / 抖 0.100 | 通 1.785 ms / 抖 0.054 | 关联与 DHCP 正常 |
| `192.168.123.161`（运控有线口） | 通 1.802 ms / 抖 0.187 | 通 **26.916 ms / 抖 34.899** | 见下方抖动说明 |
| `192.168.123.18`（拓展坞） | 100% 丢包 | 100% 丢包，**纯超时无 ICMP 不可达** | 待定 |
| `192.168.123.20`（Mid360） | 100% 丢包 | 同上 | 雷达没接，正常 |

#### 一个容易搞错的推论

`.161` 通 **不能**证明运控在转发。目的地址是运控自己的 `eth0` 时，内核走
「本地交付」，压根不过 `ip_forward` 这道门。所以 `.161` 通只说明三件事：
无线关联正常、运控这颗接口活着、ARP 正常。**转发是否开启，它一点都没说。**

同样的，`.18` 纯超时也有两种成因，PC 侧观察完全一样：

| 运控状态 | 去 `123.18` 的包 | PC 看到 |
|---|---|---|
| `ip_forward=0`（不转发） | 收到后静默丢弃，拓展坞根本收不到 | 纯超时 |
| `ip_forward=1` 无 NAT | 送到拓展坞，回包走幽灵网关 `123.1` 被丢 | 纯超时 |

#### 一条命令分辨：拿不存在的地址问它

`wifi_route_probe.sh` 新增了 §4.5 节干这件事——ping `192.168.123.254`
（该网段里几乎肯定没人用）：

| 结果 | 含义 | 结论 |
|---|---|---|
| 回 `From 192.168.123.161 Destination Host Unreachable` | 它真的去 `eth0` 上发了 ARP，失败后才回的不可达 | **转发是开的**。给拓展坞加回程路由有意义，插网线那步值得做 |
| 纯超时、什么都不回 | 目的不在本机的包直接丢弃 | **`ip_forward=0`**。加回程路由**没有用**，包根本过不去，只能走 NAT |

顺带得到一个副产品：`.18` 若是纯超时且转发确实开着，就说明运控在 `eth0` 上
ARP 成功了 —— **拓展坞是在线的**，可以排除"没上电"。

#### 两种结果各自的修法

**转发开着**（缺的只是回程路由）：

```bash
# 在拓展坞上执行，--install 装成 systemd 服务，开机自动加
sudo ~/dog_wifi_return_route.sh --install
```

`via` 必须是 `123.161`（运控），**不是 `123.1`**。

**运控不转发**（需要运控密码，先别急着插网线）：

```bash
# A) 开转发，再回拓展坞加回程路由（拓展坞那步仍要插一次网线）
ssh 192.168.12.1
sudo sysctl -w net.ipv4.ip_forward=1

# B) 直接在运控上做 NAT，拓展坞完全不用动，全程无线
sudo iptables -t nat -A POSTROUTING -o eth0 -s 192.168.12.0/24 -j MASQUERADE
```

#### 关于那 26.9 ms / 抖动 34.9 ms

同一台运控，22:43 是 1.802 / 0.187，22:49 变成 26.916 / 34.899。抖动 34.9 ms
意味着有大包排队或重传，而不是路径变化（网关那一跳始终 0.05 ms 抖动）。
两个可能：

1. **ch149 与家里 `VGE_1` 同信道重叠**，40 MHz 带宽正好骑在一起，互相抢；
2. 运控此刻 CPU 忙（`ping` 走的是本地交付，忙时会排队）。

实时点云对这个很敏感。**先在 App 里把热点信道挪到 36–44**，再复测。
脚本现在会在抖动 ≥5 ms 时单独告警，不会让你漏看。

#### 一次性打通（要插一次网线）

> **前提**：脚本 §4.5 判定为「运控在转发」。若判定为「不转发」，先按上一节开
> `ip_forward`，否则这里是白插。

回程路由只能加在拓展坞上，而此刻无线还不通，所以这一步绕不开有线。约两分钟。
**网线只在第 2–4 步存在，第 5 步起全部无线，之后永不插回**：

```bash
# 0. 用网线连 PC 的 enp131s0 和拓展坞**朝外**那个 RJ45（不是接狗身内部的口）
#    然后确认网口来了电，必须是 1 再往下，否则后面全是白忙
cat /sys/class/net/enp131s0/carrier

# 1. 先 link up，再加地址（顺序反了 NetworkManager 会把地址撤掉）
sudo nmcli device set enp131s0 managed no     # 防止 NM 反复接管
sudo ip link set enp131s0 up
sudo ip addr replace 192.168.123.10/24 dev enp131s0
ip -br addr show enp131s0                     # 确认地址还在
ping -c2 192.168.123.18

# 2. 把脚本传上去，装成服务（开机自动加，重连不丢）
scp scripts/dog_wifi_return_route.sh unitree@192.168.123.18:~/
ssh unitree@192.168.123.18
chmod +x ~/dog_wifi_return_route.sh && sudo ~/dog_wifi_return_route.sh --install

# 3. 拔网线，然后**必须**删掉临时地址，否则测出来的"通"是走有线的
sudo ip addr del 192.168.123.10/24 dev enp131s0
sudo nmcli device set enp131s0 managed yes

# 4. 回到无线侧复测（这一步起全程无线，网线不再需要）
sudo ./scripts/wifi_route_probe.sh
```

最后一步的顺序很关键：只要 `enp131s0` 上还挂着 `192.168.123.0/24`，
就会同时存在两条同前缀路由，有线那条直连的会赢，无线根本没被验证过。

### 风险（不是危言耸听）

- **运控是安全相关的控制器。** 改它的路由/NAT 一旦配错，可能导致手机 App 连不上机器人
  ——等于失去遥控手段。动之前先确认能通过别的方式急停。
- **带宽共用。** Go2 的 AP 和手机 App 的遥控图传走同一个模块，抖动会明显
  大于方案 A/B。实测 5 GHz 40 MHz 时物理速率 400 Mbit/s，但同信道若还有别的
  AP（本次现场 `VGE_1` 也占了 ch149），两者会互相抢，吞吐掉一半不奇怪。
  App 里能把热点信道挪到 36–44 就挪。
- **PC 侧还有个坑**：拔掉网线后，如果 `192.168.123.10/24` 还留在 `enp131s0` 上，
  去往 `192.168.123.18` 的包会继续往那块没载波的网卡送，形成黑洞。要么删掉这个地址，
  要么加一条更具体的路由指到 Wi-Fi 那头。

## 5. 方案 D：5 GHz 点对点网桥

一对 CPE（如 UBNT LiteBeam、TP-Link CPE 系列）做透明桥接。适合室外、大场地、
金属货架多的厂房。室内用属于杀鸡用牛刀。

## 6. 无论哪条通路，Wi-Fi 上都要做三件事

1. **关省电**——空闲后 RTT 会从 3 ms 跳到 100 ms 以上
   ```bash
   sudo iw dev wlan0 set power_save off
   ```
2. **DDS 改单播**——很多 AP 会丢弃或限速多播
   ```bash
   export CYCLONEDDS_URI=file:///path/to/dds.xml
   ```
3. **固定 IP**——在路由器里做 DHCP 绑定，否则每次换地址都要改 `EDGE_HOST`

细节见 [02-network-and-dds.md](02-network-and-dds.md) 第 3–5 节。

## 7. 怎么验证

```bash
./scripts/wifi_path_check.sh
```

它按「路由 → 链路类型 → 去程 → **回程** → 抖动」五步走，最后给结论。
其中第 4 步专门测回程——这是 C 方案最容易失败、也最难自己想到的一环。

### 7.1 切换 Wi-Fi 会切断你自己的远程协助

**这是实际动手前必须先想清楚的一件事。** 一台典型的开发笔记本只有一个无线网卡，
而它往往同时是公网出口：

```console
$ ip route show default
default via 192.168.50.1 dev wlp132s0 proto dhcp metric 600
```

把 `wlp132s0` 从家里路由器切到 `Go2-XXXXXX` 热点，**公网出口就没了**。
此刻如果正在用 SSH 远程操作、或者在和 AI 助手对话，连接会立刻断开，
而且断在半路时你不知道命令执行到哪一步。

这不是理论风险。真机上有三种典型翻车方式：

| 翻车方式 | 现象 | 后果 |
|---|---|---|
| 远程 SSH 进这台 PC | 会话直接冻结，`ping` 超时 | 只能物理接触机器恢复 |
| 靠公网 API 的对话式协助 | 消息发不出去 | 无人给你读结果 |
| 用 `nmcli` 一次性写脚本切换 | 恰好在切换那一刻报错 | 停在"网卡已断、新连接未成"的中间态 |

所以按下面的顺序做。

### 7.2 离线体检：先说结论再切网

`scripts/wifi_offline_probe.sh` 就是为这个场景写的。它把全部判断做完，
写进 `logs/wifi_probe_<时间戳>.log`，**不需要联网、也不需要有人在旁边**：

```bash
cd ~/FLMap.2

# ① 先在终端里开着（此时还有网，什么都不影响）
./scripts/wifi_offline_probe.sh          # 这一步顺便验证脚本本身能跑

# ② 切 Wi-Fi 到 Go2 热点，拔掉网线，然后重跑
./scripts/wifi_offline_probe.sh

# ③ 切回原来的 Wi-Fi，把日志交给协助者
cat logs/wifi_probe_*.log | tail -60
```

它比 `wifi_path_check.sh` 多做了三件离线必需的事：

1. **判断包到底走了哪块网卡**——`ip route get` 的结果如果是 `enp131s0`
   而不是无线口，说明有线上的 `192.168.123.10/24` 直连路由比默认路由更精确，
   把包全抢走了。这时测的不是无线，结论无效。
   修法：`sudo ip addr del 192.168.123.10/24 dev enp131s0`
2. **记录公网是否还在**——顺便确认"断了"是预期，而不是别的问题
3. **把狗端视角一起存下来**——地址、默认路由、运控可达性、幽灵网关检查

### 7.3 想保持在线？给 PC 第二条出口

如果不想经历"断线盲测"，最省事的办法是给 PC 一条独立的公网通路：

| 办法 | 成本 | 说明 |
|---|---|---|
| **手机 USB 共享网络** | ¥0 | 最常见。Ubuntu 内核自带 `rndis_host`（安卓）和 `ipheth`（iPhone），插上 USB 就多一个 `usb0`/`enx*` 接口，默认路由自动切过去。这样 Wi-Fi 可以安心去连 Go2 热点 |
| 有线网口接第二个路由器 | ¥0（若有） | 但你的 `enp131s0` 正被 Go2 占用，除非先拔掉——那就没意义了 |
| USB 无线网卡 | ¥60 | 见方案 A。一块网卡连 Go2，一块连公网，从此不再互相踩 |

USB 共享网络的具体操作：手机打开「USB 共享网络」→ 插 USB 线到 PC →
`ip route show default` 应出现一条 `dev usb0` 或 `dev enx...` 的默认路由。
此时切 Wi-Fi 到 Go2 热点，公网走 USB，局域网走 Wi-Fi，互不干扰。

> ⚠️ 注意这会让 PC 同时有两条默认路由。内核按 metric 选小的，通常 DHCP 给的
> USB 那条 metric 更低，会自动胜出；若不生效，手动把 Wi-Fi 的默认路由 metric 调大：
> `nmcli connection modify Go2-XXXXXX ipv4.route-metric 700`。

### 7.4 恢复不了怎么办

切到 Go2 热点后如果连不回来，别慌，两条退路都不需要网络：

1. **图形界面**点右上角网络图标，手动选回原来的 SSID。密码在 NetworkManager 里
   已经存着（`/etc/NetworkManager/system-connections/<SSID>.nmconnection`），不用重输。
2. **命令行**硬切（在本地终端，不走 SSH）：
   ```bash
   nmcli device wifi list
   nmcli device wifi connect "<原SSID>" password "<密码>"
   ```

真正危险的是"人在外面、只靠远程 SSH 进来改网卡"这种情况——那时一断就再也进不去。
**永远在本地终端做切换。**
