# 15. 3DGS 落地三条路线：边缘、半边缘、全离线

> 前提：点云阶段已完成（`docs/14` 讲了 3DGS / 3DGS-SLAM 是什么，本文讲**怎么在你现有设备上跑通**）。
> 本文不含实现代码，只给判定依据与可执行的工艺流程；每一步都写了产物和验收标准。
>
> 判定所依据的硬件数字，凡来自实测的都在表里标了「实测」，凡来自公开规格的标「规格」，
> 凡属推算的标「推算」。本次撰写时狗已关机（`enp131s0 carrier=0`，`.18` 超时），
> 狗端 CPU/GPU 频率、`nvpmodel` 档位**未能复核**，开机后应补测（见 §1.5）。

---

## 0. 一页结论

| 方案 | 谁训练 3DGS | 判定 | 一句话理由 |
|---|---|---|---|
| **A 全边缘** | 狗（Orin Nano 8 GB） | ❌ **不可行**（工程上） | 12× 算力差 + 4.4× 带宽差 + 与 LIO 抢同一块 8 GB 统一内存；单房间要 2–5 小时且会降频 |
| **B 半边缘** | 主机（RTX 5060 Ti 8 GB） | ✅ **推荐** | 狗只出位姿+关键帧，回传 20–50 MB；位姿由 FAST-LIO2 给，绕开 3DGS 最脆弱的环节 |
| **C 全离线** | 主机（重放 bag） | ✅ **可行，作兜底** | 最稳、可反复调参；代价是回传 0.3–50 GB（取决于是否压缩），现场无法预判质量 |

**推荐组合：日常跑 B，重要场景同时留 C 的原始包。** 两者的训练段完全共用（B4–B7），
差别只在数据从哪来。

## 1. 先把算力这条线量清楚

### 1.1 狗端：Jetson Orin Nano 8 GB

| 项 | 数值 | 来源 |
|---|---|---|
| SoC | Jetson Orin Nano 8 GB（Ampere GA10B） | 规格 |
| CPU | 6× Cortex-A78AE @ ~1.5 GHz | 规格 |
| GPU | **1024 CUDA** / 32 Tensor Core | 规格 |
| 统一内存 | 8 GB LPDDR5，**带宽 102.4 GB/s** | 规格 |
| 可用内存 | **7.3 GB**（系统已占 1.0 GB） | **实测** |
| CUDA | 11.4（JetPack 5.1.x / L4T R35） | 规格（需开机复核） |
| 算力 | 20 TOPS（稀疏 INT8，15 W） | 规格 |
| 磁盘 | NVMe 469 GB，已用 22 GB | **实测** |
| 满载温度 | SOC **58–62 ℃** | **实测** |
| GPU FP32（推算） | 1024×2×0.94 GHz ≈ **1.9 TFLOPS**（15 W 约 1.28） | 推算 |

关键点：**没有独立显存**。GPU 和 CPU 抢同一块 8 GB，`free -h` 看到的就是
GPU 能用的上限。这与桌面卡有本质区别——桌面上「显存不够」只是训练慢一点，
Orin 上是**系统开始 swap 甚至 OOM**，会连 FAST-LIO2 一起打死。

### 1.2 主机：RTX 5060 Ti 8 GB

| 项 | 数值 | 来源 |
|---|---|---|
| GPU | RTX 5060 Ti（GB206，4608 CUDA） | **实测**（`/proc/driver/nvidia/gpus`） |
| 显存 | 8 GB GDDR7 | **实测**（Xorg 日志 `8346624 kBytes`） |
| 带宽 | 448 GB/s | 规格 |
| FP32 | 4608×2×2.57 GHz ≈ **23.7 TFLOPS** | 推算 |
| 驱动 | 595.99.02（开放内核模块） | **实测** |
| 磁盘 | 776 GB 可用 | **实测** |

**比值**：FP32 **12.3×**，显存带宽 **4.4×**。

3DGS 训练不是纯算力瓶颈，主瓶颈在可微光栅化的 alpha 混合与原子累加，
**吃带宽**。所以真实差距介于 4.4× 与 12× 之间，取 **6–10×** 作为工程估计。

### 1.3 3DGS 训练到底吃什么

以单房间 1–3 M 高斯、30k 迭代为例（这是 3DGS 论文的默认档）：

| 资源 | 桌面 8 GB 卡 | Orin Nano 8 GB |
|---|---|---|
| 显存/内存 | 4–6 GB（图像分辨率 960×540，SH 3 阶） | 同样 4–6 GB，但**与系统共用** |
| 单次迭代 | 30–60 ms | 0.3–0.6 s（推算） |
| 30k 迭代 | **15–30 min** | **2.5–5 h**（推算） |
| 训练期温度 | — | 已 58 ℃ 起步，持续满载必降频 |

再叠加三件雪上加霜的事：

1. **和 FAST-LIO2 争内存**。LIO 常驻约 0.5–1 GB，且 ikd-Tree 随场景增长。
   训到一半 OOM 会把建图一起带走。
2. **没有预编译轮子**。`gsplat` / 官方光栅化在 aarch64 上要源码编译，CUDA 11.4 + 
   JetPack 5 的工具链很旧，编译成功率不高（这是最容易卡住一天的地方）。
3. **功耗墙**。15 W 模式下 GPU 频率被限，实际比峰值再慢 30–50%。

### 1.4 判定

必须区分两个层次，否则结论会被误读：

| | 结论 | 依据 |
|---|---|---|
| **技术可行性**（能不能跑通） | ⚠️ 有条件可以 | 单房间、<300k 高斯、SH=0、480p，能跑出结果 |
| **工程可行性**（能不能现场用） | ❌ 不行 | 每房间 1–3 h、会降频、会 OOM、无法边跑 LIO 边训练 |

**所以方案 A 的判定是「不可行」——不是"慢一点"，是"慢到破坏工作流"。**

一个直观的换算：一次 10 分钟的外业扫描，如果当场等 2–5 小时出结果，
那和回到办公室用主机算 15 分钟没有区别，而后者质量还高得多。

### 1.5 开机后应补测的三项

狗端上电后跑这三条，把 §1.1 里标「规格」的行换成实测：

```bash
# ① 真实 GPU 频率档（决定上面 1.9 TFLOPS 是否成立）
cat /sys/devices/gpu.0/devfreq/*/available_frequencies
cat /sys/devices/gpu.0/load

# ② 功耗模式（15 W 还是 MAXN）
nvpmodel -q

# ③ 是否已有 CUDA 运行时与 Python 绑定
ls -d /usr/local/cuda*; nvcc --version | tail -2
/usr/bin/python3 -c "import torch;print(torch.__version__, torch.cuda.is_available())"
```

第三项若已返回 `True`，方案 A 的门槛会低一些，但 §1.4 的工程判定不变。

## 2. 方案 A：全边缘（狗上训练 3DGS）

### 2.1 判定：不做

理由已在 §1.4。这一节保留完整的工艺流程，用途有两个：
① 将来换 Orin AGX 64 GB 时可以直接复用；② 作为 §1.4 判定的可验证依据。

### 2.2 如果一定要试：最小验证实验（半天）

先不要接相机、不要改现有建图流程，只验证"3DGS 在这块 GPU 上能不能训"：

| 步 | 动作 | 产物 | 验收 |
|---|---|---|---|
| A0-1 | 源码编译 `gsplat`（或官方光栅化） | `import gsplat` 成功 | 编译不报错 |
| A0-2 | 用 100 张公开数据集图像（如 `mipnerf360/room` 降采样到 480p）+ 现成位姿 | — | — |
| A0-3 | 限制 100k 高斯、SH=0、5k 迭代 | 训练日志 | 单迭代时间 < 0.3 s |
| A0-4 | 训练期间另开终端跑 `tegrastats` | 内存/温度曲线 | 峰值内存 < 5 GB、不 swap |
| A0-5 | 外推 30k 迭代 × 1M 高斯 | 时长估算 | 若 > 2 h 则正式判定不可行 |

A0-1 是真正的门槛。**如果 `gsplat` 编不过，方案 A 到此为止**，不必再往下。

### 2.3 完整工艺流程（仅供参考）

```
狗端（Orin Nano）
 ① 相机 + LiDAR 采集（同 §3.2 B1）
 ② FAST-LIO2 出位姿（已有）
 ③ 关键帧缓存到 NVMe（同 §3.2 B2）
 ④ 用 gsplat 训练（本机，480p / <300k 高斯 / SH=0）
 ⑤ 导出 .ply 高斯模型（几十 MB）
 ⑥ 只把 .ply 回传主机（不传图像、不传点云）
主机
 ⑦ 渲染新视角 / 转 mesh / 纹理烘焙（同 §3.2 B7）
```

第 ⑥ 步是这个方案唯一的亮点：**回传量从几十 MB 降到几 MB**。但代价是
现场 2–5 小时的等待，以及无法在主机上重跑更好的参数（图像没带回来）。

> 若将来真要走边缘，务必要把**关键帧图像也一起存盘**，否则模型训坏了无法重训。

## 3. 方案 B：半边缘（狗出位姿与关键帧，主机训练）★ 推荐

### 3.1 分工原则

一句话：**狗做它擅长的（实时、低内存、确定性），主机做它擅长的（大显存、可反复试错）。**

| 环节 | 在哪 | 为什么 |
|---|---|---|
| 传感器采集 | 狗 | 必须跟硬件在一起 |
| 时间同步 | 狗（拉 PC 授时） | 已有 `clock_sync.sh` |
| LIO 位姿 | 狗 | FAST-LIO2 已验证，10 Hz、残差 0.01 |
| 关键帧筛选 | 狗 | 数据量在这里降 100× |
| 图像压缩 | 狗（NVENC/JPEG） | 带宽在这里降 20× |
| **外参标定** | 主机（离线一次） | 需要反复迭代可视化 |
| 高斯初始化 | 主机 | 要读全量点云 |
| **3DGS 训练** | 主机 | 显存 + 可反复调参 |
| 验收与后处理 | 主机 | 同上 |

这条分工的关键洞察：**3DGS 最脆弱的两环是位姿和初始化点，而这两样 FLMap.3 已经现成。**
纯视觉 3DGS 要跑 COLMAP，弱纹理场景（白墙、走廊、地下车库）直接失败；
你的位姿是公制的、连续的、带 IMU 融合的，初始化点直接来自 LiDAR。

### 3.2 工艺流程 B0–B7

#### B0 一次性的准备：标定（0.5–1 天，**别跳**）

这是全流程最容易被低估的一步。外参差 1–2 cm，全场景双重影，
而且你调训练参数永远调不出来，因为问题不在参上。

| 项 | 做法 | 产物 | 验收 |
|---|---|---|---|
| 相机内参 | 棋盘格 30 张，多姿态覆盖画面四角，`cv2.calibrateCamera` | `camera_intrinsics.yaml` | 重投影误差 < 0.3 px |
| LiDAR→相机外参 | 同一块棋盘格同时被相机拍到、被雷达扫到；相机侧 `solvePnP` 得 `T_cam_board`，雷达侧 RANSAC 拟合棋盘平面 + 强度阈值取角点，得 `T_lidar_board`；两者复合 | `T_lidar_cam.yaml`（4×4） | 投影重合 < 2 px |
| 时间偏移 | 快速挥手/摇板，找图像与点云运动的相关峰 | `t_offset` | < 10 ms |

**外参验收必须用「投影叠图」而不是看数字。** 具体做法：取静止场景的一帧，
把 `/cloud_registered` 用 `T_lidar_cam` 投到同帧图像上，看墙角、门框、桌沿
能不能和像素边缘重合。偏了就调，别急着进 B1。

> 待实现脚本：`scripts/calib_lidar_camera.py`（棋盘格检测 + 平面拟合 + 联合优化 + 叠图导出）。
> 旧方案 `direct_visual_lidar_calibration` 也能用，但它对场景纹理要求高，室内白墙不友好。

#### B1 采集：相机接入与锁定

| 动作 | 细节 | 验收 |
|---|---|---|
| 接相机 | UVC 相机走 `usb_cam`（Foxy 有包）；Go2 前置相机走 WebRTC，需另做桥接 | `ros2 topic hz /camera/image_raw` ≈ 30 |
| **锁曝光** | `v4l2-ctl -d /dev/video0 --set-ctrl=auto_exposure=1 --set-ctrl=exposure_time_absolute=120` | 连续帧同一区域亮度波动 < 5% |
| **锁白平衡** | `--set-ctrl=white_balance_automatic=0` | 同上 |
| 关自动增益 | `--set-ctrl=gain_automatic=0` | 同上 |
| 时间戳 | 相机节点用 ROS 时钟（已与 PC 同步） | 与 `/livox/lidar` 的 `header.stamp` 差 < 10 ms |

**为什么必须锁曝光**：3DGS 假设同一表面在不同视角颜色一致。自动曝光会让
相邻帧亮度跳变，模型学出一堆花斑，PSNR 上不去，而且你找不到原因。

#### B2 边缘侧：关键帧筛选与打包

不要用固定帧率存图。用**空间采样**：

```
新帧到达时，若满足任一条件则记为关键帧：
  ① 相对上一关键帧平移 > 0.15 m
  ② 相对上一关键帧转角 > 5°
  ③ 距上一关键帧 > 0.5 s（防止原地停留时地图没更新）
  ④ 距上一关键帧 > 3 s 强制存一帧（防止长时间静止后时间轴断裂）
```

0.15 m 的依据：3DGS 需要相邻视角重叠 > 60%，720p / 水平 FOV 90° 时，
0.15 m 对应约 75% 重叠。走 50 m 路径约产生 **150–250 个关键帧**。

每个关键帧落盘为一个目录：

```
~/bags/<ts>/kf/
├── 000001/
│   ├── image.jpg          # 1280×720 q90，约 150 KB
│   ├── pose.txt           # 时间戳 + 4×4 c2w（来自 /aft_mapped_to_init）
│   └── cloud.pcd          # 该时刻 /cloud_registered 降采样到 50k 点，约 800 KB
├── 000002/
└── index.json             # 帧号、时间戳、位姿、曝光参数、外参版本
```

体积估算（200 帧）：图像 30 MB + 点云 160 MB + 位姿 0.1 MB ≈ **190 MB**。
若点云只存每秒一帧（20 帧）则降到 **35 MB**。

**降采样点云的用途**只有一个：给高斯做初始化位置。所以不需要全分辨率，
但**不能只留局部**——要保留该帧视野内 ±1 m 的近景，否则初始化会缺面。

#### B3 传输

已有千兆链路实测 **91 MB/s**，所以 190 MB 约 **2 秒**。三种方式任选：

| 方式 | 命令 | 适用 |
|---|---|---|
| 收工后整包拉 | `rsync -a unitree@192.168.123.18:~/bags/<ts>/kf/ ./data/<ts>/` | **最简，推荐** |
| 边扫边增量同步 | 同上，加 `--append-verify`，每隔 30 s 跑一次 | 想现场看进度 |
| 实时推流 | 狗端 HTTP POST 到 PC，PC 端落盘 | 需要现场实时预览渲染 |

第三条不建议一开始就做——它会把「采集成败」和「网络成败」耦合成一个故障点。

#### B4 主机侧预处理

```
data/<ts>/
├── images/            # 从 kf/*/image.jpg 平铺
├── transforms.json    # nerfstudio 格式（见下）
├── init.ply           # 从 kf/*/cloud.pcd 合并的点云，给 splatfacto 初始化
└── meta.json          # 内参、外参版本、时间偏移、位姿来源
```

`transforms.json` 是关键接口，**不需要跑 COLMAP**：

```json
{
  "camera_model": "OPENCV",
  "fl_x": 1130.0, "fl_y": 1130.0, "cx": 640.0, "cy": 360.0,
  "w": 1280, "h": 720,
  "k1": -0.12, "k2": 0.05, "p1": 0.0, "p2": 0.0,
  "frames": [
    { "file_path": "images/000001.jpg",
      "transform_matrix": [[...], [...], [...], [0,0,0,1]] }
  ]
}
```

**坐标约定是这里唯一容易错的地方**，错了两小时也查不出来：

| 约定 | 轴 | 用途 |
|---|---|---|
| ROS / OpenCV 相机系 | x 右、y 下、**z 前** | FAST-LIO2 输出 |
| OpenGL / nerfstudio 相机系 | x 右、y 上、**z 后** | `transform_matrix` 要求 |

转换只需左乘 `diag(1, -1, -1, 1)`。验证方法：随便挑一帧，用 `transform_matrix`
把 3D 点投回图像，若上下颠倒就是漏了这一步。

#### B5 训练（主机）

**先说清一个环境陷阱**（本机实测）：`python3` 默认指向 **3.13.12**，
而 `torch 2.14.1+cu130` 装在 **3.10 的 user site**（`~/.local/lib/python3.10/`）。
两个解释器互不可见，直接在默认 `python3` 里 `pip install gsplat` 会装到孤儿环境。
**所有训练相关的命令都显式写 `/usr/bin/python3.10`。**

```bash
# 环境
/usr/bin/python3.10 -m venv ~/venvs/gs && source ~/venvs/gs/bin/activate
pip install torch --index-url https://download.pytorch.org/whl/cu128   # 对齐驱动 595
pip install nerfstudio
python -c "import torch;print(torch.cuda.is_available())"              # 必须 True
```

**关于「用 LiDAR 点云做初始化」这一步，要提前知道它的真实成本**：
nerfstudio 的 `splatfacto` 在 `random_init=False` 时读的是 **COLMAP 的
`sparse/0/points3D.bin`**，不直接吃 `.ply`。两条落地路径：

| 路径 | 做法 | 代价 |
|---|---|---|
| ① 伪造 COLMAP 目录 | 把 `init.ply` 转成 `points3D.bin`（十几行 struct 写入） | 半天，一次性 |
| ② 直接用 `gsplat` 写 trainer | 自己写 DataLoader，`init.ply` 直接喂 | 1–2 天，但控制力最强 |

先走 ①（快），需要精细控制时再换 ②。**这一步不写在命令里假装一条命令能跑，
因为实际做不到。**

```bash
# 训练（路径①完成后）
ns-train splatfacto \
  --data data/<ts> \
  --pipeline.model.random-init False \
  --max-num-iterations 30000 \
  --vis viewer+tensorboard
```

8 GB 显存下的三档配置（按收益排序）：

| 开关 | 效果 | 何时用 |
|---|---|---|
| `--pipeline.model.sh-degree 1` | 显存 −30%，高光损失明显 | **先开这个** |
| 图像降到 960×540（`--pipeline.model.downscale-factor 2`） | 显存 −60%，纹理细节降 | 大场景必开 |
| 单块高斯上限（分块训练时） | 防止爆显存 | 多房间 |

耗时预期：单房间 1–2 M 高斯、30k 迭代，**15–30 min**；8 GB 卡是这个量级。

#### B6 验收

不要只看 loss 曲线，看四个指标：

| 指标 | 阈值 | 怎么算 |
|---|---|---|
| PSNR（留出 1/8 帧） | > 24 dB 可用，> 28 dB 好 | `ns-eval` |
| SSIM | > 0.80 | 同上 |
| 新视角目检 | 无"雾状悬浮物"、无重影 | 渲染绕行视频 |
| **几何一致性** | 高斯中心到最近 LiDAR 点距离中位数 < 5 cm | 点云比对 |

第三项最重要。3DGS 会为了"看起来对"长出大量悬浮高斯（floater），
PSNR 很高但几何是垃圾。如果要用它做导航或测量，必须过第四项。

#### B7 后处理

| 目标 | 方法 | 备注 |
|---|---|---|
| 只要可渲染模型 | 直接交付 `.ply`（高斯） | 几 MB–几十 MB，用 SuperSplat / antimatter15 播放 |
| 要 mesh（碰撞、测量） | 2DGS 或 SuGaR 正则化训练 → Poisson 提取 | 训练时间 ×1.5 |
| 要贴纹理的 obj | 高斯 → 深度图 → TSDF 融合 → 纹理烘焙 | 最重，一周量级 |
| 要与原有点云对齐 | 以 LiDAR 点云为基准做 ICP | 高斯模型尺度天然是公制的，无需缩放 |

---

## 4. 方案 C：全离线（整包带回，主机重算）

### 4.1 它比想象中便宜

一个常被忽略的事实：**FLMap.3 的 bag 里已经录了位姿。**

`docs/11-runbook` 的录制话题清单包含 `/aft_mapped_to_init`（位姿）和
`/cloud_registered`（世界系点云）。这意味着方案 C **不需要在主机重跑 FAST-LIO2**
（虽然能跑），直接读 bag 就行。所以全离线的额外成本几乎只是「多传数据」，
而不是「多算一遍 SLAM」。

### 4.2 数据量：先决定压缩方式，否则会翻车

| 存法 | 单帧体积 | 30 fps 下 10 min | 评价 |
|---|---|---|---|
| `sensor_msgs/Image` 原始 RGB8 720p | 2.76 MB | **≈ 50 GB** | ❌ 不要 |
| `CompressedImage` JPEG q90 | 150 KB | ≈ 2.7 GB | ⚠️ 可接受，但 CPU 编码压力大 |
| H.264 硬编码（NVENC）4 Mbps | 0.5 MB | **≈ 300 MB** | ✅ **推荐** |

Orin Nano 有 1 路 NVENC，720p30 硬件编码几乎不占 CPU。所以方案 C 的正确
做法是录 **压缩流**，不是录原始 Image。

⚠️ 但 3DGS 训练要的是**逐帧 JPEG**，不是视频。所以主机侧要多一步 `ffmpeg` 抽帧
并按时间戳与位姿对齐——视频的 PTS 和 ROS 时间戳对不上是最常见的坑，
必须靠录制时的 `ros2 bag` 时间戳反查，或在狗端同时存一份「帧号 ↔ 时间戳」映射。

### 4.3 工艺流程 C0–C6

| 阶段 | 动作 | 产物 | 验收 |
|---|---|---|---|
| C0 | 狗端 `record` 新增 `/camera/image_raw/compressed`（或 h264），其余照旧 | `scan_0.db3` | `ros2 bag info` 话题齐全 |
| C1 | `stop` → 导出 `map.pcd`（已有流程） | `map.pcd` | 点数正常 |
| C2 | 整包 `rsync` 回主机（千兆 91 MB/s） | 本地 `bags/<ts>/` | `sqlite3 integrity_check` = ok |
| C3 | 主机 `bag_to_pcd.py` 导出点云 + 抽出位姿 | `cloud.pcd`、`poses.tum` | 帧数一致 |
| C4 | JPEG 抽帧 + 按时间戳匹配位姿 | `images/` + `transforms.json` | 每帧都有位姿，无错位 |
| C5 | 走 §B5（训练） | `.ply` | 同 B6 |
| C6 | 走 §B7（后处理） | mesh / 纹理 | — |

C3 的位姿抽取可以复用现有 `bag_to_pcd.py` 的 sqlite 直读路径（狗端没有
`rosbag2_py`，主机有，但两条路输出一致，已验证）。

### 4.4 适用场景

- **重要场景**：不能再跑第二遍的地方（现场、客户处）
- **需要反复调参**：同一份数据试 5 组超参
- **要补拍**：发现某段漏了，回来补一帧标定
- **算法迭代**：将来换更好的 GS-SLAM，同一份 bag 可以重跑

## 5. 三方案对比

| 维度 | A 全边缘 | **B 半边缘** | C 全离线 |
|---|---|---|---|
| 3DGS 训练位置 | 狗 | **主机** | 主机 |
| 狗端 GPU 占用 | 满载 2–5 h | **≈ 0（只编码）** | 0 |
| 与 LIO 抢内存 | ❌ 严重 | ✅ 无 | ✅ 无 |
| 现场能否出结果 | ⚠️ 2–5 h/房间 | ❌ 不能（但能出点云） | ❌ 不能 |
| 回传量 | 几 MB（.ply） | **20–50 MB** | 0.3–50 GB |
| 主机训练时间 | — | **15–30 min/房间** | 同 B |
| 可反复调参 | ❌ 图像没带回 | ✅ | ✅ |
| 现场可判断质量 | ❌ 训完才知道 | ⚠️ 看 `status` 与点云 | ❌ |
| 实现工作量 | 3–6 周（含编译） | **1–2 周** | 3–5 天 |
| 主要风险 | 编译不过 / OOM / 降频 | **标定不准** | 存储与时间戳对齐 |
| 热风险 | ❌ 62 ℃ 满载 | ✅ 轻载 | ✅ 轻载 |

## 6. 推荐路线：B 为主，C 兜底

```
外业（现场）                     内业（办公室）
────────────────────────────────────────────────
狗：LIO + 采图 + 关键帧筛选  ──→  B: 标定 → 初始化 → 训练 → 验收
      │                              ↑
      └── 同时留一份原始 bag ─────→  C: 同样的训练段，数据源不同
```

具体执行：

1. **每次扫描都同时留 bag**（成本只是磁盘，469 GB 够存 100+ 次）
2. 现场用 B 的关键帧目录快速确认「数据够不够」（看 `index.json` 帧数与覆盖率）
3. 回办公室先跑 B（15 分钟出结果，快反馈）
4. 如果 B 的效果不满意，用 C 的原始包重跑——**因为同一份数据，只是换数据源，训练脚本不用改**

第 4 条是这个组合的核心价值：**B 是快路径，C 是保险。两者共用同一个 B4–B7。**

| 阶段 | 内容 | 工作量 | 通过标准 |
|---|---|---|---|
| **M0** | 主机环境：CUDA toolkit、PyTorch(cu128)、nerfstudio、ffmpeg | 0.5–1 天 | `ns-train --help` 能跑；`torch.cuda.is_available()=True` |

## 8. 失败模式与对策

| 现象 | 八成是 | 对策 |
|---|---|---|
| 全场景双重影 / 边缘拖尾 | 外参不准 | 回 M1 重标；用叠图逐帧检查 |
| 同一面墙颜色斑驳 | 自动曝光没关 | `v4l2-ctl` 锁死，重采 |
| 远处一片雾 | 高斯初始化点太稀 + 无深度监督 | 加 LiDAR 深度损失，或提高 init.ply 密度 |
| 训练 loss 不降 | 位姿坐标系搞错（y 轴没翻） | 检查 `diag(1,-1,-1)` |
| 显存 OOM | 高斯数 × 分辨率 | SH 降到 1、图像降到 540p、分块 |
| 渲染出"漂浮碎块" | 动态物体被固化 | 剔除含人/动物的帧；或用 `--pipeline.model.use-scale-regularization` |
| 走一圈回来错层 | LIO 无回环 | 分段训练 + 人工拼接，或引入回环后端 |
| 图像与位姿错位 1–2 帧 | 时间偏移没标 | 重测 `t_offset`；录制时加硬件触发 |

## 9. 数据与接口约定（写脚本前先定死）

```
data/<scene>/                     # 一个场景一个目录，scene = 日期或房间名
├── images/000001.jpg …           # 关键帧，按帧号命名
├── init.ply                      # 高斯初始化点云（来自 LiDAR）
├── transforms.json               # 位姿（OpenGL 约定）
├── meta.json                     # {"intrinsics":…, "T_lidar_cam":…, "t_offset":…, "source":"B|C"}
└── out/                          # 训练产物
    ├── splat.ply
    └── eval.json                 # PSNR / SSIM / 几何中位误差
```

`meta.json` 里必须记 `T_lidar_cam` 和 `t_offset` 的**版本或数值**。
同一个场景如果用不同外参训练，结果不可比——这是复现实验的最低要求。
