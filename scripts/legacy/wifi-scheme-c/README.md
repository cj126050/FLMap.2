# legacy/wifi-scheme-c/ —— 方案 C 留档（已证伪）

这里的五个脚本是 2026-10-18 那一轮"借 Go2 自带 Wi-Fi"的探针：PC 连狗自己开的热点
（SSID `13829973977`，PC 在 `12.122.x`，狗运控在 `12.1`），寄希望于运控帮忙把包
转发到 `192.168.123.0/24`。

**结论：软件层走不通。** 运控的 `ip_forward` 是关的，对目的不在本机的包静默丢弃 ——
`ping 192.168.12.1`（运控自己）通，`ping 192.168.123.161`（运控背后的运控口）通，
但 `ping 192.168.123.254`（一个不存在的地址）纯超时、连 ICMP 不可达都不回。
逐条实测记录见 `docs/19-wireless-selection.md`。

**现在的正路是方案 A**：狗插 USB 无线网卡（MT7612U），主机开 5 GHz 热点当 AP，
狗当 STA，两端同在 `10.42.0.0/24`。操作见 `docs/17-wireless-link.md`。

| 脚本 | 当年用途 | 为什么留着 |
|---|---|---|
| `wifi_path_check.sh` | 判断 PC 到狗的四条通路哪条活 | 里面对"运控是否真在转发"的判据仍有效 |
| `wifi_route_probe.sh` | 逐跳探测 `12.x → 123.x` 的转发路径 | 结论的原始证据 |
| `wifi_scan_report.sh` | 扫邻居 AP，排除隐藏 BSSID 误报 | 换场地选信道时还能用 |
| `wifi_offline_probe.sh` | 切 Wi-Fi 失联前的离线体检 | 断网自救流程参考 |
| `dog_wifi_return_route.sh` | 在狗上补回程路由（当时假设运控会转发） | 记录假设长什么样 |

> 这些脚本默认 PC 在 `12.122.x`、狗运控在 `12.1`，和现在 `10.42.0.0/24` 的
> 拓扑不同。**别在方案 A 的机器上直接跑**，它们会去改 `12.x` 的路由。
